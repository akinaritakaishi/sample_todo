# ADR 0004: 画面仕様書(docs/screens)とAPI仕様(OpenAPI)を整備し、変更時の更新を必須にする

- ステータス: 承認
- 日付: 2026-09-13

## コンテキスト

ADR 0003で、UIに影響する変更を含むPRには`docs/pr-screenshots/pr-<PR番号>/`配下にスクリーンショットを保存しPR本文に埋め込む運用を決めた。この運用について、ユーザーから「リポジトリに保存するのであれば、画面ごとの仕様を記録できる設計書フォルダを作りたい」「APIも同様にOpenAPIドキュメントを整備したい」という要望があった。

`docs/pr-screenshots/`はPRごとの動作確認の証跡（履歴）であり、「その時点でどう見えたか」を残すものだが、「今この画面がどうあるべきか」を一覧できるドキュメントにはなっていなかった。同様に、APIの仕様（エンドポイント・リクエスト/レスポンスの型）もコード（`front/server/api/`）を読まないと把握できない状態だった。

## 決定

- `docs/screens/`ディレクトリを新設し、画面ごとに1ファイル（`tasks.md`、`chat.md`）で仕様（目的・UI要素・呼び出すAPI・データの型）を記録する。各ファイルには現時点の画面のスクリーンショット（`docs/screens/<画面名>.png`）を埋め込む。
- `docs/api/openapi.yaml`を新設し、OpenAPI 3.0形式で現行の全APIエンドポイント（タスクCRUD、チャットメッセージの取得・投稿）を記録する。
- `docs/screens/`と`docs/pr-screenshots/`は役割が異なることを`docs/screens/README.md`に明記する。前者は「現在の仕様」として画面変更のたびに上書き更新し、後者は「PRごとの証跡」としてPRごとに蓄積し続ける（ADR 0003のまま維持）。
- `.claude/rules/design-docs.md`（`paths: front/app/pages/**/*`, `front/server/api/**/*`）を新設し、画面またはAPIに変更を加えたPRでは対応するドキュメントの更新を必須にする。

## 検討した代替案

- **`docs/pr-screenshots/`だけで済ませ、別途仕様書は作らない**: PRの履歴を遡れば分かるが、「今の画面仕様」を一覧するには最新のPRを探し当てる必要があり、閲覧性が悪い。今回の要望に応えるため、現在の仕様を一箇所にまとめる`docs/screens/`を別途新設することにした。
- **APIドキュメントをOpenAPI形式ではなくMarkdownの表で書く**: 手軽だが、将来Swagger UIなどのツールで読み込んだりモックサーバーを生成したりする余地がなくなる。標準形式であるOpenAPIを採用した方が長期的に扱いやすいと判断した。
- **OpenAPIドキュメントをコードから自動生成する（Nitroのルート定義から生成するツールの導入等）**: 現時点ではエンドポイント数が少なく、手書きのコストが低いため見送った。エンドポイントが増えてきたら自動生成の導入を再検討する。

## 結果・影響

- `front/app/pages/`配下の画面や`front/server/api/`配下のAPIを変更するPRでは、`docs/screens/*.md`・`docs/api/openapi.yaml`の更新が追加の作業として発生する。更新を忘れるとドキュメントとコードが乖離するため、レビュー時にも確認が必要になる。
- `docs/screens/*.png`は画面変更のたびに上書きされる（`docs/pr-screenshots/`のように蓄積はしない）。
- OpenAPIドキュメントは手書きのため、エンドポイントを追加・変更した際にドキュメントへの反映漏れが起きうる。将来的にコードからの自動生成に切り替える余地を残す。
