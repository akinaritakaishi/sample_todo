# 勉強会デモ台本

社内チャットに届いた要望を、Claude Codeが「読む → 設計してIssue化 → 実装・画面確認 → レビュー → 完了報告」まで一続きで進める様子を見せるデモ。所要時間の目安は約25分（短縮版は約12分）。

> 登場人物・発言はすべて架空（`slack-thread.md`参照）。

## 事前準備

1. リポジトリルートで`./scripts/demo-up.sh`を実行する（依存インストール、データのシードへのリセット、`front/`起動、MCPサーバー`sample-todo-chat`の登録まで一括）。
2. ブラウザで`http://localhost:3000/`（ToDo）と`/chat`の`dev`チャンネルを開いておく。
3. ToDo画面に次の5件が出ていることを確認する。

   | タスク | 期限 | 状態 | デモでの期待表示 |
   |---|---|---|---|
   | 取引先に請求書を送る | 2日前 | 完了済み | 強調しない（ガイドライン4） |
   | 経費精算を申請する | 昨日 | 未完了 | 危険（赤）＋「期限切れ」 |
   | 週次レポートを提出する | 今日 | 未完了 | 危険（赤）＋「今日」 |
   | 会議室を予約する | 明日 | 未完了 | 注意（オレンジ）＋「明日」 |
   | 備品発注リストを確認する | 5日後 | 未完了 | 通常表示 |

4. 各幕の開始地点に戻れるよう、`main`の状態を控えておく（失敗時の復旧は後述）。

デモを再実行する前は`./scripts/demo-down.sh`→`./scripts/demo-up.sh`でデータをシードに戻す。

## 進行

### 第1幕 要望を拾う（約3分）

> 「devチャンネルの最近のやり取りを読んで、ToDo画面への要望を整理して」

- 期待: `list_chat_messages`（`room: "dev"`）が呼ばれ、要望が「期限切れ／今日／明日／それ以外で見た目を変える」に整理される。
- 見せ場: 鈴木さん（今日だけでいい）と田中さん（明日も）の食い違いに気づき、佐藤さんがまとめた4区分を結論として採用する。「デザインのルールがドキュメントにある」という言及も拾う。

### 第2幕 設計してIssue化する（約5分）

> 「この要望を設計してIssueにして」（`issue-create`スキル）

- 期待: `docs/design-guidelines.md`を自分で見つけ、設計に反映する。
- 見せ場:
  - 色に加えてラベル（「期限切れ」「今日」「明日」）を併記する（ガイドライン1）
  - 鈴木さんの「行ごと真っ赤に」という要望は採用せず、ラベルと左端の線に留めると理由付きで判断する（ガイドライン3）
  - 完了済みタスクは強調しない（ガイドライン4）
- 司会の一言例: 「要望をそのまま実装するのではなく、社内ルールと突き合わせて調整しています」

### 第3幕 実装して画面で確認する（約8分）

> 「このIssueを直して」（`fix-and-verify`スキル）

- 期待: `TaskItem.vue`等を修正し、`verify-front`スキルで撮ったスクリーンショットで動作確認し、確認を挟まずにPR作成まで一気に進める（スクリーンショットはPR本文に埋め込まれる）。
- 見せ場: 修正前後の画面比較。上の表どおりの表示になっているかを会場と一緒に確認する。

### 第4幕 レビューで落とし穴を見つける（約5分）

> 「PRのレビューもやって」（`pr-review`スキル）

- Approveは全指摘（imo/nits含む）に対応可否の返信が付いたときだけ出る。Approveできない場合、`pr-review`はPRを監視して修正を待ち、PRを出した`fix-and-verify`側もPRを監視して指摘を自動で修正するので、Approveまで自動で進む（別セッションで動かすのが前提）。20分以上動きがなければ監視は自動で止まるので、デモで修正まで見せない場合は「残りは後で対応」として第5幕へ進む。

- 仕込み: 期限は`YYYY-MM-DD`の文字列で保存されている。実装で`new Date('2026-09-24')`のように変換するとUTCの0時として解釈され、日本時間と比較すると日付の判定がずれることがある。
- 期待: 実装がこの落とし穴を踏んでいればレビューで指摘・修正される。踏んでいなければ「なぜローカル日付で比較しているか」をClaudeに説明させる。
- 司会の一言例: 「速いだけでなく、日付やタイムゾーンのような見落としやすい所も見ている」
- 補足: シードデータ側（`task-store.js`）は既にローカル日付で生成するよう修正済みなので、朝の時間帯に実施しても表示の前提は崩れない。

### 第5幕 チャットに完了報告する（約2分）

> 「devチャンネルに対応完了を報告して。PRのリンクも添えて」

- 期待: `send_chat_message`が呼ばれ、ブラウザの`/chat`画面に即座に表示される。要望を拾った場所に返して話が閉じる。

## 短縮版（約12分）

第1幕 → 第3幕（Issue化を飛ばし「devチャンネルの要望に、デザインガイドラインに沿って対応して」と直接依頼） → 第5幕。

## うまくいかないときの手段

| 症状 | 対処 |
|---|---|
| MCPツールが呼ばれない・接続できない | `claude mcp list`で`sample-todo-chat`を確認。直らなければ`docs/demo/slack-thread.md`の内容を貼り付けて第1幕を続ける |
| チャット・タスクの表示が古い | `./scripts/demo-down.sh`→`./scripts/demo-up.sh`でリセット（サーバー再起動が必要） |
| 実装が想定と違う方向に進んだ | その場で指示を足して軌道修正する。時間がなければ事前に用意した完成形のブランチ・スクリーンショットを見せる |
| GitHubに接続できない（Issue・PR作成） | Issue本文・PR説明文をターミナル上に出させて見せ、作成は省略する |
