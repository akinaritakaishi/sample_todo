# 社内AI勉強会 前半デモ シナリオ（AI駆動開発パート）

> このファイルは勉強会の進行準備用ドキュメントです。実施内容そのものではなく、
> 当日の進行・デモ操作の台本としてメンテナンスしてください。
> `design-guideline.md` と `slack-thread.md` は本シナリオのデモ②で使う
> 架空の素材（各ファイル冒頭に明記あり）です。

## 0. 前提・全体像

- 対象：営業・講師（教育事業部）・エンジニア・事務職が混在、ITリテラシー高くない前提の60人規模
- 使用モデル：Claude Sonnet 5（一般提供モデル）
- 前半「AI駆動開発」の中で、①〜③の3本立てのうち①②を実施すること前提で以下を確定させる。③は状況次第（詳細は5章）。
- 意思決定の経緯（確定事項）
  1. 4部門横断のフル構成は不採用、MVPに絞った
  2. 軸は「エンジニア向けの作業→振り返り→改善ループ」（②）
  3. AIが知見を長期学習・蓄積する発展要素は不採用。振り返りはその場限りの自己検証に留める
  4. 案内文の②に上記ループを当てはめる

## 2. デモ①：要望を伝えるだけで作る（全員向け・驚き重視）

- 目的：AIの生成力そのものへの驚きを作る
- ツール：Claude Artifacts のみ（MCP連携なし）
- 時間目安：5〜8分

### 進行

1. 会場に「困っている業務・あったらいいツール」を自然文で聞く
2. その場でClaudeに指示し、動く画面が完成する過程をライブで見せる
3. 可能なら発言者や会場の数名に触ってもらう
4. 「これは今作っただけのプロトタイプ。次は実際の開発現場でどう使うかを見せます」とデモ②へ橋渡し

### バックアップネタ（会場から良い要望が出ない場合用）

会場の反応が薄い・要望が突飛すぎる場合に備え、以下3案を用意しておく。いずれも「入力→即座に画面が動く」体験になるようにする。

| # | ネタ | 見せ方のポイント |
|---|---|---|
| 1 | 経費申請フォーム | 部署・日付・金額・目的を入力→合計自動計算、簡単なバリデーション（金額未入力でエラー等） |
| 2 | アンケート集計画面 | ダミー回答データを与えて円グラフ/棒グラフで自動集計・可視化 |
| 3 | 在庫管理表 | 品目・数量・しきい値を入力→しきい値を下回ったら警告表示 |

- いずれもその場で「〇〇を作って」と自然文で頼み、数十秒〜数分で完成する様子を見せる想定
- 個人情報・実データは絶対に入力しない（案内文にある注意事項の実演でもある）

## 3. デモ②：実務ワークフロー全体をAIが回す（エンジニア向け・信頼構築）

- 目的：「実務で本当に使える相棒」という信頼をエンジニアに持たせる
- ツール：Slack MCP連携 + GitHub MCP連携
- 時間目安：12〜15分
- 題材アプリ：本リポジトリ（`sample_todo` / `front/`）のタスク管理ツール

このリポジトリには既に以下のデモ素材が用意されている。

- `docs/demo/slack-thread.md` … 総務・営業から「期限が近いタスクが埋もれて見えない、色分けしてほしい」という架空のフィードバックスレッド
- `docs/demo/design-guideline.md` … 色使い・バッジ・日付表記に関する架空の社内デザインガイドライン

これらを組み合わせて、「Slackの声 → Issue化 → 実装 → セルフレビュー → 修正 → デプロイフック」の一連の流れを見せる。

### 3.1 事前準備チェックリスト

- [ ] Slack MCP・GitHub MCP接続の前日リハーサル（接続トラブル対策）
- [ ] `docs/demo/slack-thread.md` の内容を、実際のSlackワークスペースの該当チャンネルに事前投稿しておく（当日ライブ投稿はしない。安定性優先）
- [ ] 本リポジトリを当日デモ用にフォーク/専用ブランチ運用にしておき、参加者の目の前で `main` を汚さない
- [ ] `front/` を `npm run dev` で事前に立ち上げ、Before画面を見せられる状態にしておく
- [ ] `.github/workflows/deploy-demo.yml`（本シナリオで追加）がPRマージ後に動くことを事前確認

### 3.2 Step 1: 課題提示（Slack → GitHub Issue）

Claudeに `docs/demo/slack-thread.md` 相当のSlack投稿を読み取らせ、GitHub Issueを起票させる。

**Issue文面イメージ（Claudeに生成させる想定の一例）**

```
title: 期限が近いタスクを色分けして目立たせたい

## 背景（Slackより）
- 総務・営業から、期限が近いタスクがリストに埋もれて見えないという声
- 「今日」「明日」を色分けしてほしいという要望

## 要望
- 今日が期限のタスクを赤、明日が期限のタスクをオレンジで目立たせる
- デザインルールがあるので、実装時に参照する
```

> **仕込みのポイント**：ここではあえて `design-guideline.md` の内容を
> Issueやプロンプトに含めず、「Slackの要望文だけ」を渡す。これにより、
> 次の実装ステップで色コードの独自定義や日付表記の仕様漏れが
> 自然に発生しやすくなり、後段のセルフレビューで確実に指摘が出る
> （詳細は3.4）。

### 3.3 Step 2: 実装（ブランチ作成→実装→PR作成）

Slack由来のIssueだけを渡して実装させる。想定される変更範囲：

- `front/src/lib/tasks.js` … `formatDue()` を拡張、または期限の緊急度を判定する関数を追加
- `front/src/components/TaskItem.jsx` … 緊急度に応じたバッジ/色クラスを表示
- `front/src/style.css` … `:root` の変数を拡張して色を追加

Before/Afterのアプリ画面（色分け前後）を見せられるようにしておく。

### 3.4 Step 3: 振り返り（セルフレビュー）

「このPRをレビューして、問題はないか？」とClaudeに指示し、自ら問題点を指摘させる。長期学習・蓄積は行わず、その場限りの自己検証に留める。

3.2で意図的に `design-guideline.md` を渡していないため、レビュー時に改めて
「`docs/demo/design-guideline.md` の内容と照らし合わせてレビューして」と
指示すると、以下のような指摘が高い確度で出ることを期待する（実際に出る保証はないため、必ず前日リハーサルで再現性を確認すること）。

- ガイドライン5「期限は相対表記（今日/明日/あと3日）にする」との不一致（絶対日付のままになっている可能性）
- ガイドライン3の配色コード（赤 `#E53935` / オレンジ `#FB8C00`）と実装の色が一致しているか
- ガイドライン4「新規スタイルを定義せず既存パターンに準拠」「絵文字ではなく簡潔な記号を使う」との整合性
- 完了済み（`done: true`）タスクにも警告色が付いてしまっていないか（要望文にも明記されていない観点）

非エンジニアの参加者にも伝わるよう、「事前に渡した情報が足りないと、AIも仕様書を見落とすことがある。だからレビューという工程が大事」という文脈で説明する。

### 3.5 Step 4: 改善・再プッシュ

セルフレビューで出た指摘をもとに、Claudeに同じPRへ修正を再プッシュさせる。

### 3.6 Step 5: デプロイフック

PRマージ後、`.github/workflows/deploy-demo.yml`（本シナリオで追加、`front/` のビルドとログ出力のみ・実際のデプロイは行わない）が自動起動する様子を見せる。実際の本番反映はしないことを口頭で補足する。

### 3.7 クロージング

Slack投稿からデプロイトリガーまで、人がやれば数時間〜数日かかる作業が数分で終わったことを振り返り、「自分の仕事のどこに当てはめられそうか」を全員に問いかける。

### 3.8 話し言葉台本（たたき台）

> 「今、Slackでこういう声が上がっています。読み上げますね……（スレッドを見せる）。
> これをAIに渡して、まずIssueを起こしてもらいます。」
>
> （Issue作成→実装→PR作成の様子を見せながら）
> 「もう実装まで終わりました。画面を見てみましょう。Before/Afterでこう変わっています。」
>
> （セルフレビューをさせながら）
> 「ここで一度、AI自身にレビューをさせてみます。『このPR、問題ないかレビューして』と聞いてみます。」
>
> （指摘が出たら）
> 「見てください、ちゃんと自分の実装の不備に気づいています。デザインガイドラインと照らし合わせると、期限の表記がルール通りになっていなかったようですね。」
>
> （修正→再プッシュ→デプロイ起動を見せながら）
> 「修正して、また同じPRに反映します。マージすると、自動でデプロイのステップが動き出します。もちろん今日は本番には反映されません。」
>
> 「Slackに声が上がってから、今のデプロイまで、普通なら数時間から数日かかる作業です。それが数分で終わりました。皆さんの仕事の中で、こういうやりとりに近いものはありませんか？」

> 台詞は当日の話者の言葉遣いに合わせて調整すること。

## 4. デモ②のお題選定に関する注意（確定事項）

- 非エンジニアも置いていかれないよう、変化は「画面を見れば分かるもの」にする（本シナリオでは色分け表示）
- 振り返りで確実に問題が見つかるよう、拾われやすい見落としを仕込む（3.2〜3.4の「あえて仕様書を渡さない」がその仕込み）
- リスク対策：MCP接続トラブルに備え前日リハーサル必須。Slack投稿は事前仕込み（当日ライブ投稿はしない）
