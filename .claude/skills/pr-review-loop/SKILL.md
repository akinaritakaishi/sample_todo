# PRセルフレビュー・ループ

## これは何のためのスキルか

理想的にはPull RequestのレビューをGitHub ActionsのCIで自動化したいところですが、CI実行にはコスト（実行時間・API利用料）がかかります。このスキルは、その自動化の代替として、Claude Codeのセッション内で人が明示的に「レビューして」と呼び出したときにだけ動く手動版のセルフレビューです。将来的にCIへ移行する場合も、ここで固めた「レビュー→ラベル付け→コメント→修正」の流れがそのまま設計の土台になります。

このスキルは以下の既存スキルを部品として使います。手順の重複を避けるため、それぞれの詳細（コミットメッセージ規約、クレデンシャルチェック、PR説明文のテンプレートなど）はここでは繰り返しません。

- `commit-and-pr` … コミット・push・PR作成/更新
- `code-review` … 差分のレビュー本体
- `references/learnings.md` … 過去のセルフレビューで蓄積した、繰り返し起きやすい指摘パターンの一覧（このスキル自身が読み書きする）

## 全体の流れ（1サイクル）

```mermaid
flowchart TD
    L[(references/learnings.md<br/>を読む)] --> A
    A[commit-and-pr: コミット・push・PR作成/更新] --> B[code-review: 差分をレビュー<br/>effort level = medium]
    B --> C{指摘はあるか}
    C -- なし --> D[「指摘なし」とPRにコメント]
    C -- あり --> E[must/imo/nitsに分類し<br/>該当行へインラインコメント投稿]
    E --> F[指摘を修正]
    F --> G{サイクル上限(3回)に達したか}
    G -- 未達 --> A
    G -- 達した --> H[残った指摘一覧をPRにコメント<br/>続行するかユーザーに確認]
    D --> K[一般化できる知見があれば<br/>learnings.mdへ追記]
    H --> K
```

サイクルは1で始まり、指摘がなくなる（Dに到達する）か、上限の3サイクルに達する（Hに到達する）まで、人に確認を挟まずに自律的に繰り返してください。「1サイクル終わったので次に進みます」のような逐一の確認は不要です（ただし各サイクルの区切りで、何が起きたかを一言で報告するのは構いません）。

## 各ステップの詳細

### 1. コミット・push・PR作成/更新

`commit-and-pr` スキルを使ってください。コミットすべき変更が何もない場合（例: 既存PRのレビューだけを頼まれた場合）はこのステップをスキップし、2から始めてください。

### 2. セルフレビュー

まず `references/learnings.md`（このスキルが過去のレビューで蓄積した知見の一覧）を読んでください。「記録がありません」の場合は無視して構いません。中身がある場合は、そこに書かれたチェック観点を意識しながら次のレビューを行ってください（過去に何度も指摘してきたパターンを、今回のPRでも見落とさないようにするためです）。

`code-review` スキルを使い、対象PRの差分全体をレビューします。effort levelは `medium` を指定してください（指摘の精度とコストのバランスを取るため）。ユーザーから明示的に別のレベルを指定された場合はそちらに従います。

`code-review` の `--comment` は使わず、まず指摘一覧（file・line・summary・failure_scenario・category・verdictなど）を受け取ることに専念してください。ラベル付けと投稿は次のステップでこのスキル側が行います。

指摘が0件だった場合は、PRに「セルフレビューを実施し、指摘はありませんでした。マージ可能な状態です。」という趣旨のコメントを投稿して、ループを終了してください。

### 3. 指摘をmust/imo/nitsに分類してインラインコメント投稿

[Conventional Comments](https://conventionalcomments.org/) の考え方を簡略化し、指摘ごとに次の3段階のどれかを判断してラベルを付けます。ここは機械的な一対一のルールに当てはめるのではなく、「著者がこれを読んだときにどう受け取ってほしいか」で判断してください。

- **`must:`** 修正必須。バグ・仕様違反・壊れる変更など、直さないとマージすべきでないもの。目安：correctness系の指摘で確度が高い（verdictがCONFIRMEDに相当する）もの。
- **`imo:`** 提案・意見。強制はしないが、レビュアーとして直した方がよいと考える点。目安：correctness系だが確度がやや低い（PLAUSIBLE相当）指摘や、簡略化・効率化など設計判断が絡む指摘。
- **`nits:`** 些末な指摘。命名・空白・コメントの書き方など、直しても直さなくても大勢に影響しないもの。

各指摘は、GitHub MCPのPRレビューAPI（`pull_request_review_write` で `create` → 指摘ごとに `add_comment_to_pending_review` → `submit_pending`）を使い、該当するファイル・行へのインラインコメントとして投稿してください。コメント本文は `**must:** <指摘内容>` のようにラベルを太字で先頭に置く形式にします。

### 4. 指摘の修正

must/imo/nitsのいずれであっても、指摘が1件でもあれば修正してください（「nitsだから直さなくていい」という判断はこのスキルでは取らない。ユーザーが明示的に「nitsは無視していい」等を指定した場合のみ従う）。`front/` 配下を修正した場合は、コミット前に `npm run lint` を実行して壊れていないことを確認してください。

修正が終わったら1に戻り、`commit-and-pr` で再コミット・pushします（PRは既存なので新規作成ではなくpushのみで自動的に更新されます）。

### 5. ループの終了条件

- 2に戻ったレビューで指摘が0件になった時点で、その旨をPRにコメントして終了します。
- 1→2→3→4のサイクルを3回実施しても指摘が残り続ける場合は、そこで自動修正を打ち切ります。残っている指摘一覧（must/imo/nits別）をPRにコメントしたうえで、「3サイクル実施しましたが、まだ指摘が残っています。続けますか？」とユーザーに確認してください。ここは無限ループを避けるための安全装置なので、ユーザーの指示なしに4サイクル目以降へは進まないでください。

### 6. 知見の蓄積

ループが終了する（指摘0件で終わる場合・3サイクル上限に達する場合のどちらでも）タイミングで、今回のサイクルで出てきた指摘を振り返ってください。そのうち「このPR固有の話ではなく、他のPRをレビューするときにも当てはまりそうなパターン」があれば、`references/learnings.md` の「知見一覧」末尾に、そのファイルの記入ルールに従って追記してください。

- 追記するのは一般化できるものだけです。「変数名が分かりにくい」のような1回限りの指摘ではなく、「日付は絶対表記ではなく相対表記にする社内ルールを見落としがち」のように、次回以降のレビューでも再利用できる粒度にしてください。
- 追記前に既存の知見と重複していないか確認し、重複する場合は新規追加せず既存の1行に統合してください。
- 該当する一般化できる知見がなければ、何も追記せずスキップして構いません（無理に何か書く必要はありません）。

## 注意事項

- このスキルはAIによる一次チェックであり、人間のレビューの代わりにはなりません。PRの説明文や既存の`commit-and-pr`スキルの案内どおり、最終的な承認は人が行うものとして扱ってください。
- コメント投稿・コミット・pushはいずれも実際にリモートへ影響する操作です。実行前にどのPR・ブランチが対象かをユーザーとの会話から確認し、想定と違う場合は止めてください。
