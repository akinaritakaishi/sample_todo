# セルフレビューで得た知見

このファイルは `pr-review` スキルでのセルフレビューを重ねる中で見つかった、
繰り返し起きやすい問題や気をつけるべき観点を蓄積するための場所です。

個別PR固有の一時的な指摘（「123行目のtypo」など）はここに書かないでください。
「次にどのPRをレビューするときにも通用する、一般化されたチェック観点」だけを残します。

## 記入ルール

- 末尾に追記していく。過去の記述は（間違いの訂正以外では）書き換えない
- 1エントリ = 1知見。`YYYY-MM-DD (#PR番号): 知見の内容` の形式で書く
- 「〜は〜になっていないか確認する」のように、次回のレビューでそのまま使えるチェック観点の粒度にする
- 追記前に、同趣旨の知見が既にないか目を通す。あれば新規追記せず、必要ならその1行に統合する

## 知見一覧

- 2026-09-07 (#12): ハードコードされていたデータをJSON等の外部ファイルに切り出す変更では、読み込み側に型・値のバリデーションがあるか確認する。コード内リテラルの頃は型が保証されていたが、外部ファイル化すると編集ミス（欠落・非数値など）が実行時エラーに直結しやすい。特にドキュメントで「このファイルを編集すれば変更できる」と編集を誘っている場合は指摘の優先度を上げる。
- 2026-09-17 (#17): 固定の許可リスト（チャンネルID等）に対する入力検証を追加するPRでは、書き込み系エンドポイント（POST）だけでなく読み取り系エンドポイント（GET、一覧取得系）にも同じ検証が入っているか確認する。書き込み側だけ弾くようにして読み取り側を素通りさせると、未知のキーを指定したときに「実在するが空」と「存在しない」が区別できなくなる非対称なAPIになりやすい。
- 2026-09-24 (#21): 手順・運用ルール（スキル・`.claude/rules/`・ADR）を変更するPRでは、同じ手順を言い換えて書いている他のドキュメント（各ディレクトリのREADME、別スキル、画面仕様など）が残っていないか、キーワードでリポジトリ全体をgrepして確認する。主な記載箇所だけ直して二次的な記載が古いまま残りやすく、そこを読んだ人が古い手順で作業してしまう。シードデータのように件数・内訳を複数箇所に書いているものも同様。
- 2026-09-29 (#31): Nuxt（SSR）のコンポーネントで現在日時（`new Date()`）やタイムゾーンに依存する表示・class判定を追加するPRでは、サーバーとブラウザで結果が変わりうるか確認する。食い違うとハイドレーションミスマッチになり、本番ビルドではclass等の属性が修正されずテキストだけ置き換わる不整合が起きる。判定をマウント後に限定するなどの対策が取られているかを見る。
- 2026-10-26 (#35): Claude Codeの権限設定（`.claude/settings.json`）で何かを「禁止」するPRでは、別のツールや書き方で同じことができないか確認する。`Read(...)`のdenyはReadツールにしか効かずBashの`cat`等では読める、Bashのdenyは文字列パターン一致なのでフラグの順番・書き方の違いや引数なしの形を取りこぼしやすい、など。逆に広すぎるパターン（`*+*`など）で正当な操作まで止めていないかも見る。
- 2026-10-26 (#36): Claude Codeのhookスクリプトを追加するPRでは、「検査結果としての失敗」（lintエラーなど、Claudeに直させたいもの）と「ツール自体が動かない失敗」（コマンドが見つからない、依存未インストール、起動エラー）を区別しているか確認する。両方をexit 2でClaudeに返すと、直しようのないエラーで編集のたびにブロックされ続ける。
- 2026-10-26 (#36): Node.jsのスクリプト（hook・scriptsなど）でファイルパスを判定するPRでは、区切り文字を`/`に決め打ちした正規表現・文字列比較になっていないか確認する。このリポジトリはWindows（Git Bash）でも使われており、`path.relative`/`path.resolve`はバックスラッシュ区切りを返すため、除外・対象判定が素通りしやすい。`path.sep`での分割や`[\\/]`のように両方を許す書き方になっているかを見る。
- 2026-10-27 (#37): 処理の一部をサブエージェントや別プロセスに切り出すPRでは、元のセッションが暗黙に持っていた状態（前回のレビューで付けた指摘の記憶、途中で取得した値など）が切り出し先に引き継がれているか確認する。毎回新しいコンテキストで動く側は過去の経緯を知らないため、同じ指摘の繰り返しや、取得タイミングがずれた材料（固定していないSHAで取った差分など）による食い違いが起きやすい。
- 2026-10-28 (#37): `gh api`でPRのコメントやレビューなどの一覧を取得する手順・スクリプトを追加するPRでは、`--paginate`が付いているか確認する。GitHub APIの一覧系は既定で30件ずつしか返さないため、件数が増えたときだけ後半が黙って欠け、テスト時の少ない件数では気づけない。
- 2026-11-01 (#37): `git diff --name-only`や`git status`などの出力を別のコマンドにパスとして渡す手順・スクリプトでは、`core.quotepath`の影響を確認する。このリポジトリには日本語パスのファイル（`docs/demo/`配下など）があり、既定設定ではそれが引用符付きの8進エスケープで出力されるため、そのまま`git show`等に渡すと失敗する。`-c core.quotepath=false`や`-z`が付いているかを見る。
- 2026-11-03 (#40): ターンやセッションの終わりに動くhook（Stopなど）で通知・ブロックするPRでは、通知の条件がそのセッションの作業に限られているか確認する。ブランチ全体の差分のように過去のコミットまで含む条件だと、レビューや質問だけのセッションでも作業を続けさせてしまい、依頼と無関係な編集を誘いやすい。あわせて、hookがMarkdownの表などの書式を解析している場合は、書式とパーサの結びつきがどこかに書かれているか（書式を変えると黙って動かなくならないか）も見る。
- 2026-11-04 (#40): 複数のコマンド・データ源の結果（`git diff`と`git log`、作業ツリーとコミット済みなど）を1つのMapやオブジェクトにまとめる処理では、同じキーが複数回現れたときに後の値で無条件に上書きしていないか確認する。追加・削除のようなフラグが、処理順の後ろにある「変更のみ」の記録で消え、判定が黙って変わりやすい。ORで合成するなど、どちらを優先するかが意図どおりかを見る。
