# セルフレビューで得た知見

このファイルは `pr-review` スキルでのセルフレビューを重ねる中で見つかった、
繰り返し起きやすい問題や気をつけるべき観点を蓄積するための場所です。

個別PR固有の一時的な指摘（「123行目のtypo」など）はここに書かないでください。
「次にどのPRをレビューするときにも通用する、一般化されたチェック観点」だけを残します。

## 記入ルール

- 末尾に追記していく。過去の記述は（間違いの訂正以外では）書き換えない
- 1エントリ = 1知見。`YYYY-MM-DD (#PR番号): 知見の内容` の形式で書く
- 「〜は〜になっていないか確認する」のように、次回のレビューでそのまま使えるチェック観点の粒度にする
- 追記前に、同趣旨の知見が既にないか目を通す。あれば新規追記せず、必要ならその1行に統合する

## 知見一覧

- 2026-09-07 (#12): ハードコードされていたデータをJSON等の外部ファイルに切り出す変更では、読み込み側に型・値のバリデーションがあるか確認する。コード内リテラルの頃は型が保証されていたが、外部ファイル化すると編集ミス（欠落・非数値など）が実行時エラーに直結しやすい。特にドキュメントで「このファイルを編集すれば変更できる」と編集を誘っている場合は指摘の優先度を上げる。
- 2026-09-17 (#17): 固定の許可リスト（チャンネルID等）に対する入力検証を追加するPRでは、書き込み系エンドポイント（POST）だけでなく読み取り系エンドポイント（GET、一覧取得系）にも同じ検証が入っているか確認する。書き込み側だけ弾くようにして読み取り側を素通りさせると、未知のキーを指定したときに「実在するが空」と「存在しない」が区別できなくなる非対称なAPIになりやすい。
- 2026-09-24 (#21): 手順・運用ルール（スキル・`.claude/rules/`・ADR）を変更するPRでは、同じ手順を言い換えて書いている他のドキュメント（各ディレクトリのREADME、別スキル、画面仕様など）が残っていないか、キーワードでリポジトリ全体をgrepして確認する。主な記載箇所だけ直して二次的な記載が古いまま残りやすく、そこを読んだ人が古い手順で作業してしまう。シードデータのように件数・内訳を複数箇所に書いているものも同様。
