# PRレビュー・承認

## これは何のためのスキルか

Pull RequestのレビューをGitHub ActionsのCIで自動化するとコスト（実行時間・API利用料）がかかるため、その代わりにClaude Codeのセッション内で人が明示的に呼び出して使う手動版のレビューです。

このスキルの責務は **「レビューして結果（指摘コメントと承認判断）をPRに残し、Approveできるまで修正を待って再レビューする」こと** です。コードの修正・コミット・pushは行いません。指摘の修正は`fix-and-verify`スキル（または人）が、このスキルが投稿したレビューコメントを入力として担当します。

## 入力

- 対象PR（番号またはURL）。明示されていなければ、現在のブランチに紐づくPRを`mcp__github__list_pull_requests`（`head`指定）で探し、見つかったPRで合っているかをユーザーに確認してから進める。PRが存在しない場合は、先に`commit-and-pr`スキルでPRを作るよう案内して終了する（このスキル自身はPRを作らない）。

## 手順

### 1. レビューの材料を用意する

差分のレビューと分類は`reviewer`サブエージェント（`.claude/agents/reviewer.md`）に任せる。実装したのと同じセッションでレビューすると、実装時の前提や意図に引きずられた甘いレビューになりやすく、差分の読み込みでメインセッションのコンテキストも消費するため（ADR 0009）。サブエージェントは読み取り系ツールしか持たないので、必要な材料をこのセッションでファイルに保存して渡す。

材料はすべて手順1-1で決めた1つのSHAから作る。監視中に続けてpushされても、差分と全文が別のコミットのものにならないようにするため。保存先はスクラッチパッド（なければ一時ディレクトリ）とする。

1. `gh pr view <PR番号> --json headRefOid,baseRefName`でheadのSHAとbaseブランチ名を取得し、`git fetch origin <baseブランチ名> pull/<PR番号>/head`で両方を取得する。以降、headはこの`<SHA>`で固定する
2. 差分を`git diff origin/<baseブランチ名>...<SHA>`で`pr-<PR番号>.diff`に保存する（`gh pr diff`はその時点の最新headを返すため使わない）
3. 変更されたファイルを`git diff --name-only --diff-filter=d origin/<baseブランチ名>...<SHA>`で列挙し（削除されたファイルを除く）、それぞれのhead時点の全文を`git show <SHA>:<path>`で`pr-<PR番号>-head/<path>`に保存する
4. 再レビューのときは、PR上の過去の指摘スレッド（本文が`[レビュワー]`で始まるインラインコメントと、それへの返信）を`gh api repos/<owner>/<repo>/pulls/<PR番号>/comments`で取得し、スレッドごとに`file`・`line`・指摘本文・返信本文をまとめて`pr-<PR番号>-threads.json`に保存する

### 2. reviewerサブエージェントにレビューを依頼する

Agentツールで`reviewer`サブエージェントを起動し、PR番号・headのSHA・差分ファイルのパス・head全文のディレクトリのパス（再レビューなら過去の指摘スレッドのファイルのパスも）を渡す。PRのタイトル・本文（変更の目的）は渡してよい。ユーザーがレビューの観点や厳しさを指定した場合は、それも依頼文に含める。

渡してよいのは、PR上に公開されている情報（差分・コード・タイトル・本文・指摘と返信）だけにする。実装の経緯や「ここは意図どおり」といった、このセッションの見解は渡さない（独立したレビューにするため）。過去の指摘スレッドを渡すのは、reviewerが毎回新しいコンテキストで動き、前回の指摘を覚えていないため。渡さないと、「対応しない」と回答済みの指摘が毎回新規指摘として返り、Approveに届かなくなる。

### 3. 結果を受け取る

サブエージェントは、`must`/`imo`/`nits`のラベル付きの新規指摘の一覧（file・line・summary・failure_scenario・suggestion）をJSONで返す。過去の指摘スレッドと同じ趣旨のものは、reviewer側で除いてある（`reviewer.md`参照）。分類の基準は`reviewer.md`に定義してあり、このスキルでは分類し直さない。ただし、`line`が差分に含まれない行を指していてインラインコメントを付けられない指摘は、差分内の最も近い関連行に付け直すか、レビュー本文に記載する。

再レビューのときは、過去の指摘スレッドへの返信状況の確認（手順4のApprove判定）はこのセッションで行う。サブエージェントには毎回PR全体の差分を渡し、新規指摘の判定をさせる。

### 4. レビューを提出する（インラインコメント＋承認判断）

GitHub MCPのレビューAPIで、指摘と判断を**1つのレビュー**として提出する。

1. `pull_request_review_write`（`create`）で保留中レビューを作成
2. 指摘ごとに`add_comment_to_pending_review`で該当ファイル・行へインラインコメント。本文は`[レビュワー] **must:** <指摘内容>`のように、見出し`[レビュワー]`とラベル（太字）を先頭に置き、修正担当（`fix-and-verify`）が読んで着手できるよう「何が問題か・どう直すとよいか」まで書く
3. `pull_request_review_write`（`submit_pending`）で、次の判断に従って提出

Approveするのは **「今回の新規指摘が0件」かつ「過去のレビューで付けた指摘（must/imo/nitsすべて）の各スレッドに、対応内容または対応しない理由の返信が付いている」** ときだけです。imo/nitsであっても、対応可否が返信で埋まっていない限りApproveしません。過去の指摘スレッドは`mcp__github__pull_request_read`でレビューコメントを取得して確認します。

| 状況 | event | レビュー本文 |
| --- | --- | --- |
| 新規指摘0件、かつ過去の指摘すべてに返信あり（または過去の指摘なし） | `APPROVE` | 「セルフレビューを実施し、新たな指摘はありません。過去の指摘はすべて対応可否が回答済みです。」 |
| 新規指摘0件だが、返信のない過去の指摘が残っている | `COMMENT` | 「未回答の指摘があるためApproveを保留します。」＋未回答スレッドの一覧 |
| 新規指摘がimo/nitsのみ | `COMMENT` | 「imo/nitsについて対応可否の回答をお願いします。」＋件数 |
| 新規指摘にmustを含む | `REQUEST_CHANGES` | 「must指摘があるため修正をお願いします。」＋must/imo/nits別の件数 |

レビュー本文の先頭にも必ず`[レビュワー]`を付ける（例: `[レビュワー] must指摘があるため修正をお願いします。`）。

PR作成者と同じアカウントで実行しているなどの理由でGitHubが`APPROVE`/`REQUEST_CHANGES`を拒否した場合は、`COMMENT`で提出し直し、本文冒頭に「判定: Approve相当」「判定: Request changes相当」のように明記する。

### 5. 知見を蓄積する

今回の指摘のうち、このPR固有ではなく他のPRのレビューでも通用するパターンがあれば、`references/learnings.md`の「知見一覧」末尾に、そのファイルの記入ルールに従って追記する。重複する既存の知見があれば新規追加せず統合する。一般化できるものがなければスキップしてよい。

### 6. Approveできるまで修正を監視する

手順4でApprove以外（Request changes / Comment）になった場合は、ここで終わらずにPRを監視し、修正を待ちます。

1. `subscribe_pr_activity`で対象PRを購読する（PRへのpush・コメント・レビュー返信がイベントとしてこのセッションに届く）。
2. 同時に`send_later`で20分後のチェックインを予約する。
3. イベントが届いたら内容を確認する。
   - 修正のpush、または指摘スレッドへの返信 → 手順1〜手順4を再実行し、**新しいhead上で**再レビューして提出する。新規指摘の判定は前回以降の差分だけでなくPR全体に対して行う。
   - 本文が`[レビュワー]`で始まる投稿（自分の反響）、CIのみのイベントなど、修正と無関係なもの → 無視する（動きとして数えない）。
   - `[レビューイー]`で始まる返信は修正担当からの回答として扱う。レビュワーとレビューイーが同じGitHubアカウントで動くことがあるため、投稿者のアカウントではなくこの見出しで見分ける。
   - 再レビューのたびに、予約済みのチェックインを`delete_trigger`で取り消し、改めて20分後に予約し直す（最後の動きから20分を数えるため）。
4. Approveできたら`unsubscribe_pr_activity`で購読を解除し、チェックインを取り消して手順7へ。
5. チェックインが発火した時点で、最後の動き（修正push・返信）から20分以上経っていれば監視を中止する。`unsubscribe_pr_activity`で購読を解除し、「20分間PRに動きがなかったため監視を中止しました。再開するにはもう一度`pr-review`を呼んでください」と未解決の指摘一覧を添えて報告する。

監視中はBashの`sleep`やポーリングで待たないこと（イベントとチェックインで起こされるのを待つ）。`subscribe_pr_activity`・`send_later`が使えない環境では監視を行わず、手順7の報告に「修正後にもう一度`pr-review`を呼んでください」と添えて終了する。

### 7. 結果を報告する

ユーザーに、次を簡潔に返す。

- 判定（Approve / Comment / Request changes、`COMMENT`で代替した場合はその旨）
- must/imo/nits別の件数と各指摘の要約
- 提出したレビューのURL

## やらないこと

- コードの修正・コミット・push（`fix-and-verify`の担当）
- 既存レビューコメントへの返信やスレッドのresolve（返信は修正側、resolveは人間のレビュアーが行う）
- PRのマージ
- 監視中に自分で修正を始めること（修正を待つ側に徹する。修正は同じくPRを監視している`fix-and-verify`、または人が行う）

## 注意事項

- AIによる一次チェックであり、人間のレビューの代わりにはならない。このスキルのApproveはマージ可否の最終判断ではなく、最終的な承認・マージは人が行うものとして扱う。
- レビュー提出はリモートに影響する操作なので、対象PRが想定どおりかを会話から確認し、違う場合は止める。
